# Session host protocol (Phase 6/7)

Status: offline protocol for the personal-use session host. Phase 6 defines the
fake-child contract. Phase 7 adds the real Claude Code adapter through the
official Agent SDK; see `docs/PHASE7-GATE-A.md`.

## Transport

The daemon spawns one child process with no shell and a sanitized environment.
The daemon writes JSON lines to the child's stdin and reads JSON lines from its
stdout. stderr is diagnostic only and is not parsed as protocol.

- One turn at a time.
- Every line is one JSON object.
- Unknown or malformed lines produce a local `protocol-error` event and are not
  forwarded as protocol events.
- The child must not write non-protocol text to stdout.

## Daemon → child

| Type | Fields | Meaning |
|---|---|---|
| `user-message` | `content` | Send one user message |
| `permission-decision` | `requestId`, `decision` (`allow` or `deny`) | Answer a pending permission request |
| `question-answer` | `requestId`, `answers` (question text → label or labels) | Answer a pending `question-request` |
| `stop` | none | Cancel the active turn |
| `shutdown` | none | Exit gracefully |

## Child → daemon

| Type | Fields | Meaning |
|---|---|---|
| `turn-start` | none | A turn began |
| `permission-request` | `requestId`, `tool`, optional `detail`, `detailTruncated`, `detailRedacted` | The agent needs user approval; `detail` is a bounded input summary |
| `question-request` | `requestId`, `questions` (1-4 of `{ question, header, multiSelect, allowText, options }`) | The agent asked an `AskUserQuestion`; options are 2-4 labeled choices; `allowText` permits a typed answer |
| `assistant-message` | `content` | Assistant text for this turn |
| `turn-end` | `status` (`completed`/`failed`/`cancelled`), optional `error` | Turn terminal state |
| `process-exit` | generated by the host, not the child | Child exited |

`process-exit` is emitted by the host when the child exits; the child should not
send it.

## Lifecycle

1. Daemon spawns the child in its own process group.
2. Daemon sends one `user-message` at a time. A second message while a turn is
   active is rejected with `TURN_ACTIVE`; the worker queues it instead.
3. Child emits `turn-start`, optional `permission-request`, one or more
   `assistant-message`, then `turn-end`.
4. `permission-decision` resolves the current `requestId`; a request must not be
   reused. Request IDs are unique for the entire session, including cancelled or
   undecided requests. Only one request may be pending; old, unknown or duplicate
   decisions are rejected.
5. `stop` cancels the active turn; the child must emit `turn-end` with
   `status: "cancelled"`.
6. `shutdown` asks for a graceful exit. If the child does not exit within the
   host timeout, the daemon kills the process group and waits until the group is
   empty.
7. Daemon `close()` is idempotent and always kills the process group, even if
   the direct child already exited. Cleanup failure (kill/scan not confirmed)
   throws `HOST_CLEANUP_FAILED` and can be retried; it is not reported as closed.

## Limits

- One JSONL line is limited to 256 KiB; oversized or malformed lines produce a
  local `protocol-error` and never reach the relay. After an oversized line the
  host discards bytes until the next real newline, so a valid-looking tail
  cannot inject an event.
- `assistant-message.content` is limited to 100,000 characters, matching the
  relay.
- `permission-request.detail` is limited to 2,000 characters; an oversized
  detail is a protocol error.
- `user-message.content` is limited to 10,000 characters.
- `question-answer` typed answers are limited to 200 characters (option labels
  remain capped at 100), with at most four values per question.

## Worker behavior

- `host-worker` polls commands before messages so Stop is not delayed by a batch
  of queued messages.
- A second user message while a turn is active is queued, not forwarded.
- Stop always clears the queue and does not forward the same batch, including
  while a turn-end event is still being posted.
- A transient event-post failure is retried; a persistent failure marks the
  worker failed and closes the host. A relay `session_closed` response also
  closes the host child. An idle worker detects `closed: true` on its
  commands/messages poll and stops the host without waiting for a failed write.
- `stop()` reports `cleanup-failed` with the error and can be retried; it returns
  `stopped` only after the host confirms the process group is gone.

## Phase 7 Claude Code adapter

`claude-host.mjs` spawns `claude-host-child.mjs` through the existing
`createSessionHost` process-group machinery. The child imports the external
Agent SDK and maps the protocol as follows:

| Protocol event/input | SDK surface |
|---|---|
| `user-message` | A streaming `SDKUserMessage` on the `query()` prompt iterable |
| `permission-request` | `canUseTool(toolName, input, options)`; the child waits for the matching decision |
| `permission-decision` | Resolves the pending `canUseTool` promise with allow or deny |
| `question-answer` | Resolves a pending `AskUserQuestion` `canUseTool` promise with `{behavior:"allow", updatedInput:{questions, answers}}` |
| `stop` | `query.interrupt()` in streaming input mode |
| `assistant-message` | Text blocks from `assistant` messages |
| `turn-end` | The `result` message; `interrupt()` is mapped to `cancelled` |
| `shutdown` | Ends the input iterable and calls `query.close()` |

A `deny` resolves `canUseTool` with deny; the SDK reports a tool-result error to
the model, which may continue and end the turn with `completed` (observed with a
real provider). The fake host instead simulates `turn-end failed` with
`permission-denied`. Both outcomes are valid and the Web client renders either;
do not assume deny always fails the turn.

`AskUserQuestion` always reaches `canUseTool`. A valid answer must cover every
question and use offered labels; when the question has `allowText: true` (the
default for SDK questions, matching the Claude Code "Other" choice), a
non-blank typed string of at most 200 characters is also accepted. The child
re-validates against the pending questions before resolving; an invalid or
stale answer is ignored, so the request stays pending until answered, stopped
or ended.

The child passes `permissionMode: "default"`, `permissionPrompts: "host"`,
`settingSources: []` and `persistSession: false`. It requires a fresh sanitized
environment and explicit working directory. `permission-request` carries an
optional, bounded `detail` from an allowlist: Bash command, file path, URL,
search query or task description. Common secret shapes are redacted, including
prefixed environment names, session IDs/cookies and URI userinfo; public
identifiers such as `PUBLIC_KEY` are preserved. The
`detailTruncated`/`detailRedacted` flags expose the limits to the UI.

The adapter fails closed when it cannot show a decision-relevant summary:
unknown tools, `mcp__*` tools and detail-required tools with missing input are
denied without emitting an approval card. Read-only/local tools on the
name-only safe list (`Glob`, `Grep`, `LS`, `Read`, `NotebookRead`, `TodoWrite`,
`ListAgents`, `ToolSearch`, `Monitor`, `ReportFindings`) may prompt with the
tool name alone.

## Phase 6/7 boundary

- Phase 6's fake child remains the deterministic test path.
- Phase 7's real `claude` process runs only against a loopback fake provider in
  this repository; no real provider, credential, phone or deployment is used.
- The relay stores `permission-request` events and `permission-decision`/`stop`
  commands; the phone/web client UI for them is Phase 8.
- The SDK route was selected after the Gate A spike. No PTY parser is used; see
  `docs/PHASE7-GATE-A.md`.
